## Task2
## Проблема

Під час пілоту платежі виконувалися одразу після створення. Через це не вдавалося:
- виконати платіж у заданий день або регулярно;
- скасувати платіж до виконання;
- сторнувати вже виконаний платіж протягом операційного дня;
- вести журнал усіх операцій.

## Шаблон: Command

Кожен платіж стає окремим об'єктом-командою, яка сама знає, як виконатися і як відкотитися. Створення платежу і його виконання тепер розділені в часі.

| Роль у шаблоні | Клас |
|---|---|
| Command | `IPaymentCommand`, `PaymentCommand` |
| ConcreteCommand | `TransferPayment`, `UtilityPayment`, `DepositTopUp` |
| Receiver | `Account` |
| Invoker | `PaymentScheduler` (черга, виконання за датою, скасування, сторнування) |
| Client | `DeferredPaymentsDemo` |

```csharp
public interface IPaymentCommand
{
    void Execute(DateOnly operationDay);
    void Reverse();
    void Cancel();
    IPaymentCommand? CreateNextOccurrence();
}
```

Приклад конкретної команди: пряма й зворотна дії лежать в одному класі.

```csharp
protected override void DoExecute()
{
    _from.Withdraw(Amount);
    _to.Deposit(Amount);
}

protected override void DoReverse()
{
    _to.Withdraw(Amount);
    _from.Deposit(Amount);
}
```

## Як вирішено кожну вимогу

- **Платежі в черзі та виконання в заданий день.** `PaymentScheduler` зберігає чергу. Метод `ProcessDue()` бере платежі з `ScheduledDate <= Today` і виконує їх за порядком дат.
- **Скасування до виконання.** `Cancel(id)` прибирає платіж з черги, статус стає `Cancelled`.
- **Сторнування виконаного.** `Reverse(id)` викликає `Reverse()` команди, але лише в той самий операційний день:

  ```csharp
  if (payment.ExecutedOn != _clock.Today)
  {
      _log.Write(payment.Title, $"сторнування відхилено: операційний день {payment.ExecutedOn:dd.MM.yyyy} закрито");
      return;
  }
  ```
- **Регулярні платежі.** Після виконання команда створює свою копію з наступною датою (`CreateNextOccurrence`), і планувальник ставить її в чергу. Виконана команда не змінюється, тому її можна сторнувати окремо.
- **Журнал.** Кожна подія пишеться у форматі `[дата] [джерело] подія`. Джерело показує, хто діяв: `Scheduler` або конкретний платіж (`Переказ #1`).
- **Помилки.** Якщо коштів не вистачає, команда отримує статус `Failed`, а планувальник пише це в журнал і йде далі.

## Допоміжне: Template Method

У `PaymentCommand` методи `Execute`, `Reverse` і `Cancel` самі перевіряють статус і змінюють його, а специфічну частину делегують у `DoExecute` і `DoReverse`. Тому нову команду достатньо описати двома методами, і неможливо виконати платіж двічі або сторнувати невиконаний.

## Демонстраційний сценарій

1. Створюються 3 платежі на різні дати: переказ, комунальний платіж, регулярне поповнення депозиту. Виводиться черга.
2. Комунальний платіж скасовується до виконання.
3. Годинник переходить до дати виконання решти платежів, вони виконуються. Поповнення депозиту регулярне, тому в черзі з'являється наступне.
4. Переказ сторнується в той самий день, залишки повертаються.
5. Сторнування наступного дня відхиляється, бо операційний день закрито.
6. Виводиться журнал.
